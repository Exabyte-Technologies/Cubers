## Isolation

Use different mainland and international hosts, DNS names, private networks, PostgreSQL/Redis instances, storage buckets, IAM credentials, SMTP credentials, AI secrets and backup keys. Never share a database, bucket, queue or backup location between regions. The server checks the account region on every protected request; deployment separation provides the primary data boundary.

Copy `.env.production.example` to a private `.env.production` on each host and replace every placeholder; restrict it to its owner. Database URL passwords need URL encoding. Supply that same file to Compose through `--env-file`. The API and worker read `.env.production` from the repository root by default. For another path, also set `CUBERS_ENV_FILE` to its absolute path. API, worker and admin run as unprivileged users with read-only filesystems; the HTTPS proxy uses its image's root user with limited capabilities. Only that proxy publishes ports. S3 and SMTP are external regional services; enable TLS, least-privilege IAM, encryption and private bucket access there.

Scrambles are generated inside each regional Node API by pinned cubing.js ESM workers. No Java runtime, TNoodle container or scramble-service URL is required. `SCRAMBLE_TIMEOUT_MS` controls the bounded generation/queue deadline; see [WCA-SCRAMBLES.md](WCA-SCRAMBLES.md). API shutdown drains active socket work before database/cache shutdown; the API has a 60-second Compose stop grace period. Already issued scrambles are retained through upgrades.

The API image includes Linux FFmpeg, FFprobe, Sharp and Prisma. A separate worker uses the same image without an HTTP listener. The API disables its in-process worker. Shutdown drains an active background job before closing its database/cache clients; the Compose worker has a 120-second stop grace period. One worker processes media serially; resource limits are starting values, not measured production video capacity.

Compose waits for PostgreSQL, applies reviewed Prisma migrations in a one-shot `migrate` service, then initializes authored courses/settings in a one-shot `seed` service before starting the worker/API. Migrations are not embedded in the HTTP process or run on each process restart. A deployment can change schema even if the API later refuses release-gate startup: use an isolated staging database and test migrations and restoration first. Never run the development reviewer/player fixtures on a release database. Repeated initialization preserves existing course content, publication status and version; course upgrades need an explicitly reviewed, versioned publishing operation.

The API refuses production startup unless HTTPS origins, SMTP, non-simulated AI mode, initialized independent deletion journaling and `PUBLIC_RELEASE_APPROVED=true` are configured. Keep the approval false until all requirements in `RELEASE.md` are satisfied. Mainland social/game/AI flags are separate and default false; they are administrative gates, not substitutes for permits or required technical integrations.

Prepare and initialize the required recovery overlay first; see [RECOVERY.md](RECOVERY.md). The complete media recovery, safe physical expiry and commissioning package remains unfinished, so public operation is still blocked. Encrypted database snapshots restore into sealed isolated targets; see [DATABASE-SNAPSHOTS.md](DATABASE-SNAPSHOTS.md). Build and validate configuration in staging before any public deployment:

```sh
docker compose --env-file .env.production -f infra/compose.production.yml -f infra/compose.recovery.yml config --quiet
docker compose --env-file .env.production -f infra/compose.production.yml -f infra/compose.recovery.yml build --pull
docker compose --env-file .env.production -f infra/compose.production.yml -f infra/compose.recovery.yml up --detach --no-build --wait --wait-timeout 180
docker compose --env-file .env.production -f infra/compose.production.yml -f infra/compose.recovery.yml ps
```

Run these commands from the repository root on the intended regional host only after operator release review. Keep `PUBLIC_RELEASE_APPROVED=false` during preparation; the startup command is expected to refuse production API/worker startup until that review is actually complete. AI may remain `disabled` without a key. The URL/model can be changed later through restricted admin settings and server secrets as described in the README.

On upgrades, back up the regional database first, stop the API and worker, review migrations, rebuild the matching service images and recreate the `migrate` and `seed` one-shot services before starting the new application services. Do not publish new course kinds while old completion handlers are still running; see [FIRST-SOLVE.md](FIRST-SOLVE.md). Do not use `down --volumes` on a persistent deployment: it deletes its database/cache/TLS volumes. Normal `down` preserves named volumes. Do not share Compose projects or data paths across regions.

Do not paste expanded Compose configuration into chat or logs: it may contain secrets. Pin base images by reviewed digest and scan the built images before a release. The supplied version tags are starting points, not a signed image provenance policy. Record and review the actual image IDs/digests used for every regional release.

## Disposable Docker verification

With Docker running and dependencies installed, run `npm run test:docker` from the repository root. This builds the API, migrations, admin, web and development-storage images, checks emulator persistence and CORS, then creates independent CN and INTL Compose projects with synthetic credentials, accounts and disposable PostgreSQL/Redis volumes. Only randomly assigned loopback HTTPS ports are exposed. Caddy generates a private test authority per region; the runner verifies certificates against that authority without installing it in the host trust store or bypassing TLS verification. The current measured platform is Linux/arm64; verify Linux/amd64 separately before using that architecture in production.

The runner keeps real AI disabled, captures mail locally, and uses the lockfile-pinned S3rver development emulator in a separate container. Its wrapper denies unsigned requests, but S3rver does not cryptographically verify SigV4 signatures. This checks the application's upload/processing path, not signature security, production S3 IAM, encryption, durability or lifecycle policy. The emulator is absent from the production API image and is not a supported production storage service. Mainland social/game/AI approval flags and public release approval stay false.

Reports and service logs are saved privately under ignored `.data/docker-smoke/<run-id>/`. Logs can contain synthetic email tokens and test configuration; do not publish them. Each run removes only its own generated Compose projects and disposable volumes, retains built images, and exits unsuccessfully with resource names recorded if cleanup is incomplete. Build/pull operations need registry network access. The local test is not a hardware, native UI, internet load, backup-restoration, operating-law or production-security certification.

Shorter teaching sequences use migration 37 and versioned optional course content. Upgrade compatible clients before publishing the new teaching. Old empty download requests retain the original v1 packet; new clients explicitly request the bounded alternatives. Existing production course content is preserved by seeding and must be changed through the MFA-protected draft/review/publish flow. The fixed local-preview update utility is development-only and is not shipped in images. See [LESSON-ALTERNATIVES.md](LESSON-ALTERNATIVES.md).

## Staff commissioning

Use the compiled [operator staff workflow](STAFF-ACCESS.md) to bootstrap the first administrator, enroll an independent second administrator and verify both authenticators and separate recovery custody. The CLI can run from the runtime image with an owned private operator volume; it does not start an API listener or make email/AI calls. It requires existing email-verified adult accounts and never sets identity/adult eligibility flags.

For the staff-security migration, stop all old API/authentication processes before applying migration 202610170005_staff_access, then start only the matching new image. Mixed old/new login implementations would not consistently enforce one-use codes. A rollback requires closed ingress, session/token revocation and reviewed factor/counter state; do not silently restart an older authenticator implementation.

All target sessions and verification/reset tokens are invalidated on access changes. Codes are usable once per current thirty-second step; wait for a new code after enrollment/login. Test recovery with one-use custody and an independent administrator before opening ingress. Bootstrap, role changes and MFA recovery have local synthetic software checks; actual operator review, encrypted secret custody, disaster recovery and production acceptance are separate work.

Keep an independent encrypted deletion journal and authenticated current inventory outside the database backup being restored. Regional binding, durable acceptance and pre-listen replay are implemented; see [RECOVERY.md](RECOVERY.md). [Encrypted database snapshots and sealed restores](DATABASE-SNAPSHOTS.md) pass real regional dump/restore drills. Actual regional alert/latency/provider acceptance, vault control/target-inventory and standalone snapshot expiry, fresh commissioning and independent production storage custody remain unfinished. This is an outstanding release requirement, not a verified capability.

Restore drills must use isolated networks and disabled email / AI / public endpoints. Restore a selected backup, apply any subsequent migrations, revoke restored sessions and verification tokens, replay the deletion journal, process expired evidence, and verify row counts, private object permissions, authentication, consent and regional boundaries. ## Monitoring and scaling

Monitor `/v1/health`, process restarts, database connections/slow queries, Redis memory and evictions, queue failures/age, media processing time, SMTP failures, S3 availability, moderator backlog, deletion backlog and evidence-retention deadlines. Use aggregate metrics and redacted logs; never log passwords, bearer tokens, AI keys, raw prompts, signed media URLs or consent documents. Configure a staffed alert channel before release. The connected private service-health page and unexposed regional Compose monitor report aggregate queue/worker/backlog/retention signals and redacted local alert/recovery events. See [OPERATIONS.md](OPERATIONS.md) for thresholds, probes and infrastructure coverage still required. Actual external alert delivery remains an operator commissioning requirement.

The measured local test connected 100 players in 13 rooms for 60.78 seconds, completed 17,113 operations with zero failures, and approved 100 reconstructed solves. Recorded p95 latency was 76.52 ms. It used one API process with local PostgreSQL and Redis; it did not measure TLS, internet latency, physical recordings or video processing. The report is `artifacts/load-test.json`.

A subsequent Pyraminx run on the updated puzzle integration connected the same 100 players / 13 rooms for 60.47 seconds, completed 16,087 operations with zero failures, and approved 100 reconstructed solves. Latency was p50 31.10 ms, p95 39.83 ms and p99 44.21 ms. The report is `artifacts/load-test-pyraminx.json`; reproduce it with `CUBERS_LOAD_PUZZLE=pyraminx npm run test:load`. Different puzzle scrambles and code revisions mean these runs are not a controlled speed comparison. The same loopback and single-process limits apply.

The present WebSocket implementation is single-process. Do not horizontally scale it until a Redis Socket.IO adapter, shared routing strategy and multi-node membership/disconnect behavior are implemented and load-tested. REST and background work also need bounded database pools, media worker isolation and resource limits. Avoid scheduling transcodes on the same process/host used to establish game capacity until tested under realistic combined load.

## Security configuration

Read [SECURITY.md](SECURITY.md) before staging. Development API/web commands default to loopback. A physical-device test may explicitly set `HOST=0.0.0.0` and use a trusted private network with a firewall and an explicit API URL; never expose development fixtures, Metro, S3rver, SMTP or PostgreSQL to the internet.

The production Compose network reserves `172.30.70.2` for the HTTPS proxy and trusts only that address. Automatic assignments are restricted to `172.30.70.128/25`. If its subnet overlaps a host network, change the subnet, automatic pool, proxy address and both trust settings together. Test spoofed forwarded headers through the actual proxy, and keep API port 3000 private. The configured API/worker resource limits are starting values; measure memory/CPU with real video workloads before sizing production.

`MEDIA_DAILY_BYTES` defaults to 1 GiB of reserved uploads per account per rolling 24-hour window. Configure storage ingress upload-duration limits, private bucket/version lifecycle rules and cost alerts. Database-backed object-removal retries last 24 hours after deletion; they do not replace storage lifecycle or the independent restore deletion journal.

Deploy matching API, worker and operator images with migration `202610180002_media_restore`. It adds restored-snapshot provenance and private per-batch/file receipts; the additive migration is not an unseal or data-access authorization. Current sealed database restores record that provenance, and media restoration refuses a different snapshot or the source bucket. Experimental earlier archives require reviewed compatibility work; never fabricate or clear the markers. See [MEDIA-RESTORE.md](MEDIA-RESTORE.md).

Deploy migration `202610180003_journal_floor` with matching API/worker/snapshot/operator images. Stop old readers/writers before any journal-format transition. Existing version-1 inventories/manifests are not silently adopted; do not overwrite accepted history or keys. Review [history-retirement compatibility](JOURNAL-RETENTION.md) before handling experimental older data. No production history was converted here.
