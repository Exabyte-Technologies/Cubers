# Apple receipt certificate status

The Apple provider now requires a current, authenticated certificate-status result for the receipt-signing chain. Enrollment and receipt replacement verify status after CMS, app, key and signed-field validation. Action challenges and assertions prepare the shared status cache outside account/database locks; protected game mutations recheck its deadline inside the existing authority transaction. Unavailable, expired, revoked and unknown results cannot authorize an action. Provider and production-ranking flags remain off.

## Trust and transport

`apple-certificate-status.ts` orders the dedicated receipt-purpose signer and its issuers to the separately pinned Apple Root CA G3. Each non-root certificate must advertise exactly one supported OCSP address in its signed Authority Information Access extension. Requests are restricted to canonical `ocsp.apple.com/ocspNN-…` URLs with no credentials, custom ports, queries, fragments or redirects. DNS results must all be public addresses; the selected address is pinned to the connection. No system trust, arbitrary endpoint, CRL fallback or successful result for missing status metadata is supplied.

Apple's published sample has OCSP addresses for its receipt signer and Application Integration intermediate. Its separate App Attest key leaf/intermediate have no AIA or CRL endpoint. That absence is not recorded as a good revocation result, and this change does not provide online revocation coverage for that key chain. Its pinned purpose, signatures, nonce, validity and operator trust-update requirements continue to apply.

The receipt certificates advertise HTTP. The client permits that exact signed address because OCSP responses are independently signed and verified; it does not upgrade blindly to a failing HTTPS endpoint or disable TLS validation. HTTPS, when advertised, retains normal hostname and certificate checks. The public-only probe on 2026-10-25 found an HTTPS hostname mismatch at the vendor hostname; the advertised HTTP service returned authenticated responses. This observation is not a promise about future vendor routing.

Only public vendor certificate identifiers are posted. No account ID, receipt, app proof, device identifier, recording or authorization credential is included. The vendor sees the server's network address. Canonical certificate-chain metadata is retained inside the existing encrypted receipt record, with its existing erasure, export-exclusion and sealed-restore behavior. Status responses are cached only in process memory.

## Verification and bounded work

`ocsp.ts` constructs a nonce-free request and binds the response to its exact issuer-name hash, issuer-key hash and serial number. SHA-1 is used only for this public certificate identifier; weak response signature algorithms are refused. Independent DER checks reject malformed/trailing data, duplicate identifiers, unsupported critical extensions, invalid times and oversized responses. OpenSSL 3 checks the response signature, authorized issuer/delegated responder and pinned chain, with default trust stores and explicit global-responder trust disabled. Delegated responders must additionally carry the issuer-signed OCSP `nocheck` lifetime policy; responders needing a separate revocation mechanism are refused. This is a restricted Apple receipt workflow, not a general-purpose OCSP service.

Responses are capped at 32 KiB. A public lookup has a five-second deadline, no retry or redirect, and a three-second socket timeout. At most two shared lookups and two resolver operations run per process; underlying work retains its slot until actual completion after cancellation. The offline verifier separately admits two processes, kills them after two seconds and removes private temporary files after process closure. These are resource bounds, not an end-to-end latency guarantee for multiple chain members or filesystem scheduling.

A good status lease lasts at most five minutes and never exceeds signed status times or certificate expiry. Status timestamps have a five-second skew allowance and a 24-hour maximum age; a response without `nextUpdate` is restricted to ten minutes from `thisUpdate`. Signed revoked/unknown results remain distinct and never authorize. Requests shared across accounts do not transfer account authority: cancellation, session/guardian changes, receipt replacement and actual database-lock waits are checked again before persistence or game mutation.

## Deployment and rollover

There is no operator switch to bypass certificate status. Enabling the Apple provider requires the same private receipt-encryption file and isolated OpenSSL executable as before. Allow the reviewed vendor OCSP service through deployment egress policy and accept outage behavior before activating the provider. Receipt refresh remains available to a current owner whose old status lease has expired; only a fully verified replacement can restore action eligibility. It cannot extend an expired or revoked key through a caller-supplied status result.

The key-policy digest now includes the status-verification version. Previously enrolled keys require fresh native enrollment; legacy encrypted receipts without authenticated chain metadata cannot silently regain trust. A planned release must explain this setup requirement to users. Changes to the App Attest root, receipt root, issuer path or status format require reviewed source/pin updates, isolated tests, a controlled deployment and fresh enrollment when the trust scope changes. This software deliberately has no automatic root download, system-store fallback or transparent legacy-key migration.

Synthetic source tests authenticate good/revoked/unknown responses, wrong roots and unauthorized signers, expired/future/contradictory times, cache sharing/cancellation and bounded timeout behavior. Authenticated HTTP/PostgreSQL tests additionally cover unavailable status, expiry across a real attempt-row wait and session revocation while the lookup is paused outside authority locks. Public certificate-only probes authenticate both published receipt-chain responses; they do not exercise Apple's authenticated receipt API or any Cubers installation.

Real signed-device enrollment, actual receipt-service credentials and refresh, current platform/issuer compatibility, regional transfer review, outage/clock/rollover operating drills and ranking acceptance remain open. Existing hardware, mainland approval and publication gates stay closed.
