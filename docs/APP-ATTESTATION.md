# Platform app-attestation implementation

The Apple workflow now connects native enrollment and account key management to persistent verification and all five critical game transitions. The [Android Standard workflow](PLAY-INTEGRITY.md) is now connected internationally with keyless action grants. Owner-requested Apple receipt updates and an explicit risk gate are connected; see [APPLE-RECEIPT-REFRESH.md](APPLE-RECEIPT-REFRESH.md). Optional periodic refresh is connected with per-key opt-in; see [APPLE-PERIODIC-RECEIPTS.md](APPLE-PERIODIC-RECEIPTS.md). Receipt-chain [certificate status](APPLE-CERTIFICATE-STATUS.md) is now required with bounded signed OCSP checks. Operator trust-rollover drills, mainland Android trust and actual signed-device acceptance remain unfinished. Production ranked play stays disabled in both communities for virtual, scanned and smart input. Synthetic signatures and an unsigned simulator compile do not establish device or competition acceptance.

## Persistent Apple workflow

Migration 43 adds verification keys, challenges and short-lived action grants with ownership/session/attempt foreign keys, immutable context, bounded lifetimes, terminal revocation and monotonic counter/version guards. The authenticated routes are `GET /v1/me/app-attestation`, `POST /v1/me/app-attestation/challenges`, `POST /v1/me/app-attestation/verify` and `DELETE /v1/me/app-attestation/keys/:id`. Responses are private; none can enable ranking. Google remains unavailable by default; its separately enabled international Standard workflow uses keyless action challenges/grants described in [PLAY-INTEGRITY.md](PLAY-INTEGRITY.md).

Enrollment challenges bind the native key identifier's hash, current user, full session, community and verifier policy. The client signs the exact UTF-8 `clientData` returned by the server. Only its SHA-256 hash and context digest are stored. Challenges expire within two minutes and move atomically from pending to verifying to used/failed. Two enrollment slots bound expensive verification; a capacity rejection leaves the challenge pending for retry. Duplicate concurrent enrollment returns a conflict; the same owner's later challenge can recover the existing key summary after a lost response. A key cannot be reassigned to another account.

Action challenges additionally bind the exact attempt/room snapshot and version, operation and strict request-body digest. Signature verification occurs outside account locks; a final transaction rechecks current authority, receipt, membership, attempt phase/deadlines, verifier policy and the current counter. A successful assertion advances the persisted counter and creates a grant valid for at most thirty seconds. Recording, inspection, start, finish and evidence handlers now consume supplied `appProofId` grants inside their current-authority mutation transaction. The strict shared request contract excludes the grant credential from the signed body digest. A failed action, including a zero-row conditional update, rolls consumption back. Supplying a proof never silently bypasses verification, including on a casual attempt. Production ranked creation/participation remains separately refused.

Every HTTP attempt mutation now rechecks full account/guardian/session authority, membership and attempt state under ordered locks, including ordinary virtual and scanned input. Competition proof operations take event/entry locks before room/attempt locks, matching cancellation and withdrawal. Evidence may be submitted after a round closes if the solve finished before its deadline and the current event/entry, recording permission and thirty-day attempt window still permit submission. This does not permit starting or finishing a late solve. Changed snapshots require a fresh proof.

Verified enrollment receipts use AES-256-GCM under a private operator file outside the database. Authentication binds community, account, key-record UUID and native-key hash. The storage file must be an absolute canonical path, a single-link regular file owned by the service user or root, with no group/other access or execute permission. Its strict JSON format is `{ "version": 1, "id": "<UUID>", "key": "<canonical base64 of 32 random bytes>" }`. Keep each installation's secret separate and outside images/source/config exports. No operator secret is provisioned by this milestone.

The retained key scope includes the app identifier, distribution, receipt-key identifier and both pinned trust-root fingerprints. Build-allowlist changes invalidate outstanding challenges/grants while allowing existing keys to sign an approved upgraded build; enrollment and latest verified builds remain separate. Changing the storage secret identifier or trust scope requires fresh trust enrollment. Manual receipt updates are now connected. Optional periodic scheduling is connected. The status-verification version is now part of key scope; older keys require fresh native enrollment. Receipt-chain OCSP checks are required. Operator key/issuer/root rollover and real-device acceptance remain open before activation.

Own-key listing and revocation remain available after a child's learning consent is withdrawn, while new challenges/proofs require current learning permission. Revocation and expiry clear the public key and encrypted receipt; terminal metadata is removed after thirty days. Requests are pruned after two days, expired grants are deleted, and session deletion cascades its challenges/grants. Account deletion revokes keys before normal erasure. Sealed restoration revokes restored active keys, clears their public keys/receipts, retains counters and invalidates session-bound proofs. Exports and guardian views contain summaries, excluding receipts, identifiers, fingerprints, counters and proof grants. Bilingual privacy text describes these records.

`APP_ATTESTATION_APPLE_ENABLED` defaults to `false`. Configuration requires `APP_ATTESTATION_APPLE_APP_ID`, exact comma-separated `APP_ATTESTATION_APPLE_BUILDS`, `APP_ATTESTATION_APPLE_DISTRIBUTION`, private `APP_ATTESTATION_RECEIPT_KEY_FILE` and absolute OpenSSL 3 executable `APP_ATTESTATION_OPENSSL_PATH`. Production refuses development/TestFlight distribution. Mainland availability additionally requires both `CN_GAMES_APPROVED` and `APP_ATTESTATION_CN_APPROVED`. These software gates do not establish regulatory approval; keep them off pending the remaining acceptance work.

## Native Apple connection

Profile → App verification reads owned key summaries, explicitly enrolls a supported iOS device and removes verification. Removal remains usable without current learning consent. Reset revokes a known server binding before discarding local metadata; unexpected key loss/reinstallation requires deliberate recovery rather than silently creating new keys. Known full-session and guardian deletion flows erase the corresponding device cache. Server deletion invalidates trust independently of any remaining inaccessible hardware key.

The pinned `@expo/app-integrity` **55.0.17** adapter uses `generateKeyAsync`, `attestKeyAsync` and `generateAssertionAsync`. Its Swift source hashes the exact UTF-8 server `clientData` before calling DeviceCheck, matching the server protocol. Key identifiers, enrollment phase and server key-record UUID are saved per account/community using SecureStore's `WHEN_UNLOCKED_THIS_DEVICE_ONLY`; no attestation object, receipt, grant or login token is persisted there. A short-lived pending enrollment proof stays in memory only for a same-session foreground retry. Lost successful replies recover through the server's ownership check.

Hardware operations serialize across accounts. A timeout returns an interruption outcome while the underlying SDK job retains its slot until actual completion. Backgrounding, account/consent changes, navigation and explicit cancellation invalidate late callbacks before another request can be sent. Already committed server operations are not undone by client cancellation. Revocation can proceed even if an uncancellable SDK job stalls. Ordinary and scheduled ranked-room controls use the proof client; smart transitions flush telemetry first and use the same flow while their upload bridge holds its operation slot.

The module loads lazily. The Apple adapter returns unavailable on old clients without its module, simulators, unsupported iOS devices, Android and web; Android uses its separate Standard adapter described above. There is no fabricated Apple proof; there is no fabricated proof. Both server provider gates and all hardware/ranking activation remain off. Apple is contacted only after an explicit enrollment on a supported device and an enabled server. No real Apple verification was performed here.

`CUBERS_APP_ATTEST_ENV=development` or `production` optionally adds the iOS `com.apple.developer.devicecheck.appattest-environment` entitlement during Expo native generation. It is absent by default. Regenerate and rebuild the development client after changing the setting; supply the operator's registered App ID/team and matching server distribution/build allowlist. Do not activate the deployment merely because a build compiles. [Expo's SDK 55 documentation](https://docs.expo.dev/versions/v55.0.0/sdk/app-integrity/) marks the module alpha; pin and review upgrades and accept actual signed devices before launch.

## Implemented verification

`apps/api/src/attestation/apple.ts` checks an App Attest key's dedicated certificate chain and signatures, certificate validity and understood critical constraints, nonce, application identifier, environment, initial counter, credential identifier and complete P-256 COSE public key. A factory pins Apple's public App Attestation Root CA by its DER SHA-256 digest, with no client-selected trust anchor. Assertion checks bind the signed authenticator data to the expected request challenge and public key, require a strictly increasing counter, and check the configured distribution and exact bundle version. Policies are copied and frozen before use.

Bounded CBOR/DER parsing rejects duplicate map/extension keys, nonminimal lengths, indefinite formats, unsupported values, trailing data and excessive size/depth. Certificate and signature operations use Node's OpenSSL-backed cryptography. Errors expose a fixed message and a safe internal classification, rather than incoming proofs or credentials. This is a purpose-specific parser and dedicated two-certificate App Attest path, not a general WebAuthn or PKIX implementation. Future certificate-path/format changes require review.

Current Apple documentation requires `apple_validation_category_01` and `apple_bundle_version_01` authenticator extensions. The policy distinguishes App Store, TestFlight and development distribution; launch categories are compared to exact four-byte values. Missing properties, other executable categories and unknown builds are refused. This strict interpretation and the published little-endian example still require real-device and current-OS acceptance. An older or unsupported proof does not receive a successful result.

`apps/api/src/attestation/google.ts` sends an opaque Standard Integrity token only to the fixed HTTPS Google decoder, using a server-provided access token and refusing redirects. It bounds credential/decode waits and response size, then checks the decoded request hash, both package identifiers, issuance/freshness/deadline, explicit signer/build allowlists, Play recognition, Play licensing and device integrity. Google test verdicts, basic-only/virtual-device verdicts, extra unknown signers and changed requests are refused. Success returns selected verification metadata, excluding tokens and credentials. The international provider now connects Google SDK service-account authentication through a validated private operator file; no real credential or authorization was provisioned.

## Independent receipt verification

`apps/api/src/attestation/apple-receipt.ts` independently verifies the receipt's CMS signature and certificate path with OpenSSL 3, followed by the signed receipt fields. The public Apple fixture's receipt chains to Apple Root CA G3, separately pinned by its DER fingerprint; the key attestation uses the different App Attestation Root CA. Receipt signing also requires the dedicated `1.2.840.113635.100.12.15` certificate extension and digital-signature usage. A generic Apple-signed certificate is insufficient. Future issuer/root changes require review rather than a fallback to system trust.

The verifier accepts a single bounded definite/streamed BER CMS envelope, checks the complete extent, allows one signer, and validates strict certificate paths at a server-owned time. It disables default CA paths/stores and external OpenSSL configuration. The signed ASN.1 fields must have unique identifiers, understood attribute versions, exact app/environment/type, the independently attested P-256 key, creation within five minutes, and a future expiry. The public example stores a DER certificate in its key field; a canonical SPKI is also supported, with both compared through the exact public key. Fresh `RECEIPT` values additionally require valid refresh timing and a bounded nonnegative risk metric; `ATTEST` receipts provide no risk metric.

A shared verifier admits at most two processes, each with a two-second execution deadline and a 16 KiB input limit. It invokes an absolute, server-owned OpenSSL 3 executable with separate arguments and no shell. Temporary directories use mode 0700, proof/output files use 0600, and all work is removed before capacity is released. Cancellation and timeout kill the actual child; errors have fixed messages. The production Linux image already includes OpenSSL 3. Local macOS tests explicitly use Homebrew OpenSSL 3; unsupported tools fail closed rather than dropping trust-isolation options. Filesystem scheduling time is not represented as an end-to-end latency guarantee.

`AppleEnrollmentVerifier` joins key and receipt checks, compares their app/environment and returns the receipt only after independent verification. The lower-level key primitive still labels its raw output `unverifiedReceipt`; callers must not treat that output as verified enrollment. Neither lower-level API grants user/session/attempt authority. The persistent service described above wraps these checks with authenticated enrollment, encrypted storage and action binding. Manual and optional periodic refresh authorization and an explicit operator risk threshold are connected. Production factories also require [current receipt-chain certificate status](APPLE-CERTIFICATE-STATUS.md). Operator trust updates and real-device/service commissioning remain open.

## Published Apple fixture discrepancy

The public [validation guide](https://developer.apple.com/documentation/devicecheck/attestation-object-validation-guide) retrieved on 2026-10-20 includes a signed example whose certificate nonce equals `SHA256(authData || challenge)`. Recomputing the [verification article's](https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server) prescribed `SHA256(authData || SHA256(challenge))` gives a different value. Its example also cannot serve as evidence of an accepted Cubers release/build.

`tests/helpers/apple-published-attestation.json` retains the public example, source URL and downloaded document digest. A regression verifies its genuine certificate chain within its certificate-validity window and refuses its nonce under the documented algorithm. No raw-challenge fallback was added. This is a calculation from the downloaded example, not a claim that Apple's device service produces invalid proofs. Synthetic keys/certificates separately exercise positive and tampered cases. Neither fixture is a real Cubers installation.

1. Commission the implemented owner-requested receipt refresh and explicit risk policy; commission the optional periodic worker and the implemented receipt-chain OCSP policy, then accept operator trust-update/rollover procedures. Apple challenges, admission limits, action bindings, counters, cleanup and recovery now have synthetic server coverage.
3. Accept the connected Apple transition/recording/evidence workflow on actual signed devices, including frame changes, slow proof delivery, background/disconnect races and every real competition deadline. A generic installation check cannot certify footage or a solve.
4. Exercise the implemented native account-scoped key management, deliberate loss/reinstallation recovery, user-facing removal and deletion on real devices and both regional account configurations.
5. Accept the connected Android/iOS proof/server workflows on actual signed builds through Apple and Google. Developer/test verdicts cannot qualify a public ranked result.
6. Configure operator-owned Apple identifiers/builds, Google Cloud/Play authorization, signer fingerprints and exact release versions. Test outages, revoked/expired credentials, key and counter races, forged/replayed/wrong-action proofs, real OS/build upgrades and monitoring. Production activation requires separate reviewed acceptance.

[Expo SDK 55's app-integrity module](https://docs.expo.dev/versions/v55.0.0/sdk/app-integrity/) documents native APIs for App Attest and Play Integrity Standard requests and marks its alpha status. The Apple adapter/optional entitlement and international Android Standard proof client are connected. Web, simulators, missing services and unsupported devices return unavailable.
