# Optional automatic Apple receipt updates

Implemented 2026-10-22. The receipt service and production rankings remain disabled. All provider acceptance uses synthetic transport and test signing roots; no real Apple or AI request, credential provisioning, native-device test or fresh UI inspection occurred.

## Account choice and operation

Profile → App verification provides a separate bilingual choice for each active Apple key. It explains that automatic updates send the saved receipt to Apple even while signed out, excluding Cubers names, posts and recordings. Existing and newly enrolled keys default to opted out. Enabling requires a current full owner session, current learning/guardian eligibility, the exact key version and an approved regional service. Opting out remains available after service or learning permission is withdrawn and succeeds despite a stale displayed version. It invalidates the pending lease; a late result cannot restore opt-in.

The catalogue and authorized owner/guardian exports include the choice and next scheduled time. Internal lease identifiers, failure counts, encrypted receipts and provider errors are omitted. Account deletion removes associated records. Revocation and expiry clear the schedule with stored public keys/receipts. Sealed restoration revokes restored keys and clears all automatic choices, schedules, leases and failure counters; a backup cannot reactivate them.

## Deployment

Keep `APP_ATTESTATION_APPLE_AUTO_REFRESH=false` unless automatic processing has been commissioned. Enabling it requires `APP_ATTESTATION_APPLE_RECEIPT_ENABLED=true` and the existing Apple receipt credentials, risk policy and regional approval. Those flags do not establish regulatory approval or provider acceptance. User opt-in is independently required.

The separate background worker runs a bounded sweep through the existing minute-based maintenance queue, after privacy/erasure housekeeping. When automatic processing is enabled, mount the same private receipt-encryption key and DeviceCheck credential file into the API and worker at their configured canonical paths, using restricted ownership/permissions. Do not bake keys into images or backups. A manual-only installation does not load verification secrets into the worker. Use a controlled restart after credential changes.

Each sweep selects at most five due keys. A thirty-second database lease coordinates separate workers without holding account, guardian or key locks during provider work. An abandoned lease can be reclaimed. At admission and final persistence, the service locks and rechecks the current owner, guardian relationship/learning permission, opt-in, active/unexpired key, policy, original encrypted receipt and lease. Ordinary assertion counters may advance meanwhile; refresh preserves their current value. Every key mutation still advances the existing monotonic version. The database identity/terminal-state/counter guard is unchanged.

Scheduling waits at least one minute and strictly after the signed not-before date, and never moves beyond receipt expiry. The signed date is checked again before a request, so altered scheduling metadata cannot authorize an early request. Provider deferral leaves current trust unchanged. Failures retain the old encrypted receipt and use bounded exponential backoff up to six hours. The existing eight-second exchange deadline and two underlying provider slots remain enforced. Shutdown cancels pending work and rejects late results. If expiry is reached, fresh enrollment is required; retries do not extend trust.

A successfully verified replacement is encrypted for the same account/key/community. A high risk count remains subject to the operator policy and does not automatically authorize game proofs or rankings. There is no cross-region fallback. Issuer-status/revocation and trust-root rollover handling remain unfinished.
